### 5.1 优点

1. 未注册 promptId 会报错。

3. 缺少变量/多余变量会报错。

这套机制本身是正确的。

### 5.2 P1：关键编排链路仍在手工 

在  /  orchestrator 中仍大量出现手工字符串替换。

风险：

1. 占位符拼写误差不会统一 fail-fast。

### Phase A（快速收益，1-2 天）

1. 打通 ：handler -> ai-runtime -> llm options -> provider 映射。
2. 给  增加 JSON repair 子步骤，对齐 。

### Phase B（中等改造，3-7 天）

1. 抽取通用  基础组件，减少两条 orchestrator 重复分叉。
2. 将核心 prompt 构建迁移到 （先主路径，后长尾）。

1. 逐步收口 legacy  路径到统一 runtime 协议。

3. 统一验收看板：成功率、retry 次数、repair 命中率、token 超限率。

## 8. 验收标准（建议）

### 8.1 功能验收

1. 指定  的步骤，底层请求可观测到对应生效值（或 clamp 后值）。
2.  在 JSON parse 错误时可进入 repair 子步骤并成功回收。
3. 关键 prompt 缺变量时在入口 fail-fast，不进入模型调用。

### 8.2 稳定性验收

1. 两条主链路在同类 parse 错误下的成功回收率差异明显收敛。
2. 单位任务平均 retry 次数下降。
3. 超长输出导致的失败比例下降。

### 8.3 可观测性验收

1. 任一失败任务可通过  快速定位。
2. 可直接看到预算参数与实际模型调用参数差异（若有 clamp 必有日志）。

## 9. 风险与边界

1. 不建议一次性重写所有 prompt 与全部任务链路。
2. 不建议新增兼容层兜底，避免未来清理负担。
3. 优先做“参数打通 + 修复策略对齐 + 主路径 prompt 校验化”，收益最大且风险最低。
