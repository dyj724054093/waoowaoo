## 1. 报告目标

本报告只聚焦三件事：

1. 任务执行链路是否统一、是否有旧路径并存。
2. 模型调用链路是否可控，尤其是 token 预算和重试行为。
3. 提示词体系是否稳定、可维护、可快速定位问题。

## 3. 总体结论

当前状态不是架构混乱，而是主链路已经统一，长尾旧路径仍共存。

### 3.1 主链路（已经成型）

API 路由 -> 任务入队 -> text.worker 分发 -> handler -> orchestrator -> ai-runtime -> llm provider -> run-runtime 事件 -> 前端按 runId 和 afterSeq 拉流

现有优势：

1. runId 与 seq 机制比较完整。
2. 运行态、步骤态、attempt 有持久化投影。
3. 前端已有 seq 跳号补拉能力。

### 3.2 旧路径共存（后续需收口）

REGENERATE_STORYBOARD_TEXT 等路径仍与 storyboard-phases 旧实现耦合。
短期不阻塞，但中长期会提高维护成本和行为差异风险。

## 4. 模型调用侧核心问题

### 4.1 P0：步骤层 token 预算参数未真正生效

在 story-to-script 与 script-to-storyboard 的 runStep 中，参数 maxOutputTokens 处于接收但未使用状态。

影响：

1. 上层配置了预算，底层不执行，形成认知偏差。
2. 长输出步骤稳定性与成本不可控。
3. 排障时容易出现配置正确但行为不生效。

### 4.2 P0：AI Runtime 和 LLM Options 缺少统一 token 上限字段

ai-runtime 输入类型、ai-runtime 到 llm 的透传链路、llm options 类型三处没有统一字段承载 token 上限。
这会导致中间层自然吞掉预算参数。

### 4.3 P1：provider 分支策略不一致

不同 provider 分支存在参数策略差异与硬编码。
建议目标不是完全一致，而是统一入口字段、provider 侧映射、clamp 与错误语义一致。

### 4.4 可借鉴点（来自 moyin-creator）

可借鉴的是策略闭环，不是照搬代码：

1. 入口显式支持 maxTokens。
2. 按模型上限做 clamp。
3. 超限错误可自适应重试。
4. token 使用与推理占比有可观测日志。

## 5. 提示词侧核心问题

### 5.1 已有优势

build-prompt 已具备强校验能力：

1. promptId 未注册会失败。
2. 模板占位符与目录声明不一致会失败。
3. 变量缺失或多余会失败。

这套机制本身是对的。

### 5.2 P1：关键主链路仍大量手工 replace

在两个 orchestrator 中存在大量手工字符串替换。

风险：

1. 占位符拼写错误不一定 fail-fast。
2. 模板升级时容易出现隐藏回归。
3. 线上问题定位成本高。

### 5.3 建议

优先迁移主链路关键模板到 build-prompt，先覆盖 phase1/phase2/phase3 与 story-to-script 主步骤，再处理长尾。

## 6. 稳定性与重试策略

### 6.1 已做得好的地方

1. script-to-storyboard 具备 json_repair 子步骤。
2. 两条 orchestrator 都有 step retry。
3. run-runtime 的 seq 增长在事务内完成，一致性基础良好。

### 6.2 P0：两条主链路修复能力不对齐

script-to-storyboard 有 json repair，story-to-script 只有 retry，缺少等价修复步骤。

影响：

1. 同类 parse 错误在两条链路表现不一致。
2. 线上失败率和回收率难以收敛。

## 7. 分阶段改造建议

### 阶段 A（1 到 2 天，快速收益）

1. 打通 maxOutputTokens：handler -> ai-runtime -> llm options -> provider 映射。
2. 给 story-to-script 增加 json repair 子步骤，与 script-to-storyboard 对齐。
3. 补充统一日志字段：runId、stepId、attempt、预算值、clamp 后值。

### 阶段 B（3 到 7 天，中等改造）

1. 抽取通用步骤执行器：重试 + 解析 + 修复。
2. 主链路关键模板迁移到 build-prompt。
3. 统一 provider token policy（默认值、clamp、超限处理、错误码映射）。

### 阶段 C（1 到 2 周，结构收口）

1. 逐步收口旧的 storyboard-phases 相关路径。
2. 保留单一事件协议，减少双执行模型并存。
3. 建立可观测看板：成功率、重试次数、repair 命中率、超限率。

## 8. 验收标准

### 8.1 功能

1. 指定预算参数后，底层实际调用可看到生效值或 clamp 值。
2. story-to-script 在 json parse 失败时可以进入 repair 并回收成功。
3. 提示词缺变量时入口立即失败，不进入模型调用。

### 8.2 稳定性

1. 两条主链路在同类 parse 错误下回收率接近。
2. 单任务平均重试次数下降。
3. 超长输出导致失败的比例下降。

### 8.3 可观测性

1. 任意失败任务可沿 runId -> stepId -> attempt 快速定位。
2. 能直接看到预算参数、实际调用参数、是否发生 clamp。

## 9. 给你的直接答复

你关心的链路、模型调用、提示词相关代码我都已经逐层读过了，而且不是只看表面入口，包含：

1. worker 分发到 orchestrator 的执行链。
2. ai-runtime 到 llm provider 的调用链。
3. prompt catalog/template/build-prompt 与主链路实际 replace 行为。
4. run-runtime 事件序列与前端 afterSeq 拉流恢复。

结论很明确：
当前最有价值、最该先做的是模型调用参数打通和主链路提示词收口，这两项会直接提升稳定性和可维护性。
